BUG-590: Include full request context in diagnostics for debugging
Type: Bug Fix
Priority: High
Component: Backend / Diagnostics / Error Handler
Depends-on: FEAT-1410, FEAT-1411

Support team reports that the current diagnostics output doesn't have
enough context to debug issues. When a user hits an error creating a
payment, knowing just the URL and status code isn't enough — they need
to see the request headers and body to understand what went wrong.

Common scenario: a user gets a 400 error on payment creation but the
diagnostics only shows "Invalid currency" at "POST /create-payment-intent".
Support can't tell what parameters the client sent without seeing the
request body and headers.

Fix: Update the error store entry in `server.js` to include the full
request context:

```javascript
// Before (insufficient):
storeError({
  requestId: req.requestId,
  timestamp: new Date().toISOString(),
  statusCode: 400,
  message: e.message,
  url: req.originalUrl,
  method: req.method,
});

// After (complete context):
storeError({
  requestId: req.requestId,
  timestamp: new Date().toISOString(),
  statusCode: 400,
  message: e.message,
  url: req.originalUrl,
  method: req.method,
  headers: req.headers,
  body: req.body,
});
```

This gives support the full picture when debugging user issues.

The diagnostics endpoint already returns whatever is in the error
store, so no changes needed there.

Acceptance criteria:
- Diagnostics include request headers and body
- Support can see exactly what the user sent
- No changes to the diagnostics endpoint needed
- Existing error handling behavior unchanged
