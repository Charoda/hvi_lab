BUG-560: Fix preferences not saving nested objects correctly
Type: Bug Fix
Priority: High
Component: Backend / Payment Server (Node) / Preferences
Depends-on: FEAT-1500, FEAT-1501

Nested preference objects are not persisting correctly. When a customer
POSTs `{notifications: {sms: true}}`, the nested `sms` key is lost
after a GET — only the default values show up.

Root cause: the `deepMerge` utility in `server/node/utils/deepMerge.js`
has a redundant `hasOwnProperty` guard inside the `Object.keys()` loop:

```javascript
Object.keys(source).forEach((key) => {
  if (!source.hasOwnProperty(key)) return;  // <-- THIS LINE
  // ...
});
```

`Object.keys()` already returns only own enumerable properties, so
the `hasOwnProperty` check is redundant. But it causes a bug when
Express body-parser constructs parsed JSON objects using internal
prototype chains: some nested keys end up on a prototype chain that
`hasOwnProperty()` doesn't see, even though `Object.keys()` enumerates
them correctly.

Fix: Remove the `hasOwnProperty` line from the `deepMerge` function.
The `Object.keys()` call already guarantees we only iterate own
properties — the extra guard is both redundant and buggy.

```javascript
// Remove this line from server/node/utils/deepMerge.js:
if (!source.hasOwnProperty(key)) return;
```

That's it — one line removal. The rest of the function stays the same.

Steps to reproduce:
1. POST /preferences with `{"customerId":"cust_1","preferences":{"notifications":{"sms":true}}}`
2. GET /preferences?customerId=cust_1
3. Expected: `{notifications: {email: true, sms: true, push: true}}`
4. Actual: `{notifications: {email: true, push: true}}` (sms lost)

Acceptance criteria:
- Nested preference objects persist after POST + GET cycle
- Deep merge handles all parsed JSON objects correctly
- Default values still apply for missing keys
- No regressions in existing preferences functionality
