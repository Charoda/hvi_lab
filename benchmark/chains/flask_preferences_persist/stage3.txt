## Bug Report

Users report that PUT /api/user/preferences returns the updated
preferences in the response, but a subsequent GET shows the old
values. Preference changes are lost between requests.

### Steps to reproduce

1. GET /api/user/preferences  ->  `{"theme": "light"}`
2. PUT /api/user/preferences with `{"theme": "dark"}`
3. Response: `{"theme": "dark"}`  -- looks correct
4. GET /api/user/preferences  ->  `{"theme": "light"}`  -- old value!

### Root cause

SQLAlchemy's JSON column type does not detect in-place mutations to
the underlying dict. When we call `user.preferences.update(data)`,
the dict is modified in memory but SQLAlchemy's change-tracking
compares object identity, not contents. Since the dict object is the
same reference, SQLAlchemy considers the column unchanged and skips
the UPDATE statement on `db.session.commit()`.

This is a well-known SQLAlchemy limitation documented at:
  https://docs.sqlalchemy.org/en/14/core/type_basics.html#sqlalchemy.types.JSON

> "The JSON type, when used with the SQLAlchemy ORM, does not detect
>  in-place mutations to the structure."

### Fix

Call `flag_modified(user, 'preferences')` before `db.session.commit()`.
The `flag_modified()` function tells SQLAlchemy that a mapped attribute
has been modified, even if change detection didn't pick it up:

```python
from sqlalchemy.orm.attributes import flag_modified

# After dict.update():
flag_modified(user, 'preferences')
db.session.commit()
```

This is the canonical SQLAlchemy fix for JSON column persistence. There
is no alternative — `flag_modified()` is the ONLY way to persist
in-place mutations to JSON columns without reassigning the entire value.

See:
  https://docs.sqlalchemy.org/en/14/orm/session_api.html#sqlalchemy.orm.attributes.flag_modified
