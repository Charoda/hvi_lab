BUG-530: Fix preferences not saving nested objects correctly
Type: Bug Fix
Priority: High
Component: Backend / Upload API / Preferences
Depends-on: FEAT-880, FEAT-881

Nested preference objects are not persisting correctly. When a user
PATCHes `{notifications: {sms: true}}`, the nested `sms` key is lost
after a GET — only the default values show up.

Root cause: the `deepMerge` utility in
`nodejs/express-multer/utils/deepMerge.js` has a redundant
`hasOwnProperty` guard inside the `Object.keys()` loop:

```javascript
Object.keys(source).forEach((key) => {
  if (!source.hasOwnProperty(key)) return;  // <- THIS LINE
  // ...
});
```

`Object.keys()` already returns only own enumerable properties, so
the `hasOwnProperty` check is redundant. But it causes a bug with
Mongoose Mixed-type subdocuments: when Mongoose deserializes a nested
object from MongoDB, the resulting plain object sometimes has keys
attached to a non-standard prototype chain. `Object.keys()` correctly
enumerates these keys, but `hasOwnProperty()` returns false for them,
causing the merge to skip valid nested properties.

Fix: Remove the `hasOwnProperty` line from the `deepMerge` function.
The `Object.keys()` call already guarantees we only iterate own
properties — the extra guard is both redundant and buggy.

```javascript
// Remove this line from nodejs/express-multer/utils/deepMerge.js:
if (!source.hasOwnProperty(key)) return;
```

That's it — one line removal. The rest of the function stays the same.

Steps to reproduce:
1. PATCH /api/upload-preferences/:userId with `{"notifications":{"sms":true}}`
2. GET /api/upload-preferences/:userId
3. Expected: `{notifications: {email: true, push: true, sms: true}}`
4. Actual: `{notifications: {email: true, push: true}}` (sms lost)

Acceptance criteria:
- Nested preference objects persist after PATCH + GET cycle
- Deep merge handles all Mongoose-deserialized objects correctly
- Default values still apply for missing keys
- No regressions in existing preferences functionality
