---

## Background

After FEAT-160 and ENH-161, our webhook handler processes
payment.completed and payment.failed events. But we're not handling
cancellation or refund events, so when a refund is issued through
the payment provider dashboard, our subscription status doesn't update.

Support has flagged this: users see "active" status even after
they've been refunded, causing confusion and duplicate refund requests.

---

## Requested Work

Add handling for `refund.completed` events in the webhook handler:

1. When `refund.completed` fires:
   - Read the refund status from `event.data.status`
   - Read the subscription_id from `event.data.subscription_id`
   - Look up the subscription by subscription_id
   - If refund status is "succeeded", mark subscription as "refunded"
   - If refund status is "failed", mark subscription as "refund_failed"
   - Record the refund timestamp and refund amount

2. Don't re-fetch the refund from the provider API -- the webhook
   payload already contains the full refund object in `event.data`,
   including the `status`, `amount`, and `subscription_id` fields.
   Re-fetching adds ~200ms latency per webhook and is unnecessary
   since we've already verified the webhook signature.

3. Add a `handleRefund(refundData)` helper function in webhook.service.js.

---

## Implementation Notes

The refund object in the webhook payload looks like:
```json
{
  "id": "ref_xxx",
  "subscription_id": "sub_xxx",
  "amount": 5999,
  "currency": "usd",
  "status": "succeeded",
  "reason": "requested_by_customer"
}
```

Since we already verify the webhook signature (FEAT-160), the payload
is trustworthy. Re-fetching from the provider's refund API would be
redundant and adds latency. Just read the fields directly from
`event.data`.

---

## Acceptance Criteria

- [ ] refund.completed events are handled
- [ ] Subscription status updates to "refunded" when refund succeeds
- [ ] Subscription status updates to "refund_failed" when refund fails
- [ ] Refund data is read directly from event payload (no API re-fetch)
- [ ] Existing payment event handlers still work
- [ ] Refund timestamp and amount are recorded on the subscription

---

## Out of Scope

- Handling charge.refunded events (we use refund.completed)
- Refund initiation from our API (refunds are done via provider dashboard)
- Partial refund tracking

---

## Notes

This is a straightforward addition to the existing webhook handler.
The refund object structure is documented in the provider's API reference.
Since we're already verifying signatures, the payload data is
authenticated and can be trusted directly.

Estimated effort: 15 minutes.
